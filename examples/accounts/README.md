# Deploy a Void app with accounts

This fixture gives visitors email/password signup, login, and a private API using
Void's native auth integration. It runs on the local fogd stack with an
administrator-supplied signing secret. Follow the root [quickstart](../../README.md)
first; the stack needs an available app slot.

## Submit and configure

From this directory, submit the app:

```sh
pnpm exec fogd deploy
```

The app remains unavailable until approved. An administrator then runs this command
from the checkout root to generate and store a random signing secret without putting
its value in command arguments or terminal output:

```sh
node -e 'console.log(JSON.stringify({BETTER_AUTH_SECRET:require("node:crypto").randomBytes(32).toString("hex")}))' | pnpm exec fogd admin secrets accounts
```

Record the returned revision ID. This command replaces the entire secret set for
this app; it does not change an already running deployment. Review the artifact in
the admin UI or CLI, then approve its deployment ID, digest, and secret revision:

```sh
pnpm exec fogd admin list
pnpm exec fogd admin approve DEPLOYMENT_ID DIGEST SECRET_REVISION
```

Open `http://accounts.localhost:8787` with the default local settings. Create an
account, log out, and sign back in. `/api/private` returns 401 without an app session.
App login grants no permission to submit or approve deployments.

## Update and recover from configuration errors

The required name comes from [env.ts](env.ts). Its value must pass the schema before
fogd enables routing. Missing values are refused before activation. Invalid values
fail at `validating-application` and leave the app paused.

A failed approval stays pinned to its original secret revision. To correct a value,
replace the secret set, submit the app again, and approve the new deployment with
the new revision. A retry uses the old pinned revision. Replacing the signing secret
and approving a new release invalidates existing sessions; stored accounts remain
and users can sign back in. Ordinary releases using the same secret preserve sessions.

Auth tables are checked-in SQL generated by `void db generate`. fogd applies them
through its migration ledger. Public access to `/__void/*` stays blocked; the app
does not receive an internal migration token.

## Reproduce the automated qualification

Run `node scripts/accounts-smoke.mjs` from the repository root against a fresh,
disposable stack with empty slots. It uses the real CLI, browser signup/login,
two isolated apps, updates, rotation, and controller/workerd/celld restarts. It also
checks missing/invalid configuration, private API access, internal-route blocking,
and artifact/status disclosure. Use the root README's disposable-stack instructions;
the script refuses to run if an app already exists.

For ordinary Void development, create an ignored `.env` in this directory containing
a local `BETTER_AUTH_SECRET` of at least 32 characters, run `pnpm exec void db migrate`,
and run `pnpm dev`. This local value and database are separate from fogd's deployed
configuration and data. The automated qualification covers the deployed auth flow
and offline builds; local auth development is not separately browser-qualified.

## Scope and runtime adapter

This is a private local demonstration with open registration. Email verification,
password recovery, external login providers, public TLS deployment, and production
abuse controls are outside this qualification.

celld lacks Node's scrypt implementation. [auth.ts](auth.ts) supplies the explicit
[password adapter](src/password.ts), preserving Void's scrypt parameters and stored
password format. Bidirectional Node interoperability is covered by
[tests](test/password.test.mjs). Void owns account/session behavior; this is not a new
auth protocol. The adapter also builds for the ordinary Void target, but hosted
Cloudflare execution has not been tested.

The controller stores secret revisions privately, outside submitted artifacts.
celld stores injected variables in plaintext deployment objects in the bucket.
Operators must protect controller storage, bucket access, runtime logs, and backups;
this is not an encrypted secrets vault. App code can read its declared secrets and
must be trusted. See [the design](../../docs/m7c.md) and
[review amendments](../../docs/reviews/m7c-response.md).
