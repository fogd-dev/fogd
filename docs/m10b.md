# M10b proposal: retire an app without handing its identity to the next app

This proposal extends U9 after capacity reporting. Retirement is an operator action
with retained recovery material. It must stop application execution, free one fleet
for a different app, and preserve the other app. It must not claim secure erasure or
hostile-tenant isolation.

## Proposed first target

Qualify Docker first. Kubernetes retirement remains explicitly unsupported until a
separate PVC/generation adapter passes the same tests. Use whole-installation
maintenance downtime for the first implementation; route pausing is insufficient to
stop existing requests, alarms, and runtime background work.

An administrator prepares retirement against the app's exact active deployment and
receives a durable plan. The controller pauses that route and refuses further
submissions, approvals, and secret updates for the app. The operator takes a stopped
installation backup, retaining all private state. The local retirement command
requires that completed snapshot and verifies the stopped installation still matches
the plan before any storage or metadata change.

The operator command allocates a fresh bucket prefix, two fresh replica volumes,
and new replica identities for the retired fleet. It preserves the other fleet's
identities, resources, and records. Old bucket state and replica volumes remain
retained and are never mounted into the new generation. Controller metadata retains
an app-name tombstone and approval history, so stale proposals or tokens scoped to
the retired name cannot reactivate it. A replacement app uses a different name and
separately issued authority. Reusing retired app names is outside this slice.

## Failure contract

The operation records a private journal before effects. It stages configuration
before changing active metadata, and leaves every writer stopped until the final
receipt. A failed or interrupted attempt must either resume the same recorded plan
or refuse startup with an actionable recovery path; it must never guess which
replica generation to use. Operator files and controller state must agree before
ordinary startup is allowed. No automatic namespace, bucket, or volume deletion
belongs in this operation.

Backups can resurrect retired apps and credentials: restoration must warn about
that boundary. The retained old generation is recovery material, not a usable
second deployment. The operator must keep it stopped. Existing single-admin and
trusted-application assumptions remain; scoped runtime storage credentials require
separate qualification.

## Acceptance evidence

| Requirement | Validation |
| --- | --- |
| Retirement is admin-only and pins the active artifact/plan | Reject deploy-token requests, stale digests, duplicate/conflicting requests, and absent apps |
| Retiring app cannot receive updates or private configuration changes | Exercise submission, approval retry, and secret replacement after preparation |
| Every application writer stops before generation change | Reject running containers, foreign writable mounts, and interrupted stop; no completed receipt |
| New fleet has fresh storage and runtime identities | Compare old/new volume, node, and bucket-prefix identities; inspect retained old state without mounting it into new workers |
| Replacement cannot inherit old app data or authority | Retire notebook, deploy a different app, verify empty D1/R2/DO state and refusal of old proposals/scoped tokens |
| The other app survives maintenance with the same sessions and data | Keep accounts in the other fleet and verify login/session and records after startup |
| Interrupted retirement does not admit mixed generations | Inject failures before/after metadata and configuration writes, restart the command, and verify deterministic resume or safe refusal |
| Retention/deletion semantics are explicit | Document retained private snapshots, volumes, prefixes, histories, and tombstones; no automatic deletion |

## Review questions

Is an in-place stopped journal the smallest safe path, or should the first adapter
transform a snapshot into a fresh installation and leave the entire source stopped?
The latter reuses fresh-storage recovery but changes the installation handoff and
copies the unaffected app. Which path has fewer untestable intermediate states?

Should preparation be a controller mutation or an entirely offline operation on an
already stopped installation? The online plan gives immediate admission denial but
adds a lifecycle state and recovery obligations before execution. An offline-only
command may be simpler if it still pins the active deployment and prevents later
startup with stale configuration. Choose after review and record the rationale.
