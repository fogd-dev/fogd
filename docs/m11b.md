## Product outcome

Two browsers share a small checklist. A checked item acknowledged by the server
survives a supported replica restart. A disconnected browser visibly reconnects,
recovers the latest board, and retries any unacknowledged operation without applying
it twice. Updates may preserve WebSockets while changing their server handlers; the app
must handle both that path and reconnection.

Use native Void APIs, not a fogd-only realtime client. App builders should get typed
messages, inferred resources, ordinary builds, scoped deployment and exact approval.
This is a qualification fixture, not a general collaborative editor or team product.

## Source findings

At Void revision `6ef71cfe1b3364e04fd0ec261f7f00bef6aeb99f`,
`packages/void/src/runtime/ws.ts` exposes `defineRoom`, durable storage in hook
contexts, and a browser `connect` helper with reconnect and pre-open buffering.
`ws-server.ts` uses `acceptWebSocket`, socket attachments, and hooks on the generated
Durable Object. `docs/guide/websockets.md` documents stable route/resource names and
warns that users resolved at connect time are not refreshed during a session.

The separate `void/live` API multiplexes topics over SSE. Its client reconnects and
resubscribes, but `runtime/live.ts` and `live-server.ts` do not persist application
events. The guide explicitly says delivery is at most once and requires app-owned
replay. Its Durable Object also schedules subscriber-pruning alarms. We must not
mistake those alarms for qualification of arbitrary background app effects.

fogd's `packages/runtime/src/gateway.js` forwards the original request after route
lookup and healthy-replica selection; it does not buffer response bodies or replay a
sent mutation. WebSocket upgrades and SSE must be exercised through this actual
workerd path. celld has WebSocket transport in `crates/celld/main/websocket.rs` and
Durable Object socket handling in its JS harness; API presence is not acceptance.

[Cloudflare's WebSocket guidance](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)
distinguishes hibernation from disconnect/reconnect behavior. Native Void uses the
hibernation API; this slice must test the pinned self-hosted implementation rather
than infer identical failure behavior from that API name.

## Proposed contract

Start with a named `defineRoom` WebSocket route and a bounded checklist snapshot.
Store the board, a monotonic revision, and operation receipts in SQLite-backed
Durable Object storage. Use synchronous SQL inside `storage.transactionSync` to
commit the operation and receipt together before sending acknowledgment. No network
calls or sends belong inside the transaction. Reusing an operation ID with different content fails.
A duplicate returns the prior result without another mutation, even after the room
reaches its capacity. Look up receipts before checking capacity or new-operation
validity. No memory-only state is authoritative. Test concurrent clients.

Use explicit operations such as setting an item's checked value, not toggling it.
Bound the fixture to 100 items and 1,000 receipts per room, including semantic
rejections. Persist those rejections so retries cannot turn a previously refused
operation into an edit after room state changes. When the
receipt bound is reached, refuse new operations; do not evict deduplication receipts
and silently weaken retry semantics. This is a fixture capacity limit, not a
platform-wide quota or garbage-collection design. Return typed terminal rejections
with an operation ID for conflicts, capacity, and invalid operations; remove these
from pending storage and show the reason. Validate before persisting browser input,
but keep the server envelope schema broad enough to reject saved old-version
operations explicitly rather than repeatedly closing the socket with 1007.
Malformed unrelated protocol traffic may still close; it must not drive a saved-op
reconnect/resend loop. Test invalid, conflicting, and over-cap pending operations.

The native browser client keeps one local-storage key per room/operation before send,
removes them only after matching acknowledgment, and resends after reconnect with
the same IDs. Send only after the native socket reports open, avoiding duplicate
app retries on top of Void's pre-open buffer. A full authoritative snapshot arrives on every connection and after
successful mutation. Render only nondecreasing revisions within a connected session. If a fresh
connection reports a lower revision than the browser last observed, show an explicit
rollback/reconciliation state and stop automatic writes; do not silently stall or
claim preservation beyond the restored snapshot. The baseline restore test stops
clients before backup and makes no later writes. A snapshot does not by
itself acknowledge a pending operation; resend it for its receipt. Lost acknowledgments
are unknown outcomes, not permission to generate replacement IDs.

The example is anonymous and local-only. Reject missing or cross-origin `Origin`
headers in browser upgrades. Compare origin scheme/host against the trusted
`x-forwarded-proto` and `x-forwarded-host` set by workerd, whose gateway strips client
spoofs; do not rely on the backend request scheme. Put semantic size limits in typed
operation rejection, and retain transport-level bounds for malformed large frames. No private-user, membership, session-revocation,
or hostile-tenant claim. Existing application authentication is a separate feature
and this fixture must not imply it refreshes an established WebSocket's identity.

## Acceptance and sequencing

1. Build and stage the native room with the existing runtime adapter. Record any
   required upstream patch explicitly. Do not replace native Void if a runtime gap
   is discovered. Obtain review before adopting a shim or narrowing the contract.
2. Deploy two isolated apps through ordinary scoped upload and approval. Before
   approval, upgrades must not reach app code. Two browsers on one app converge;
   the other app and another room do not inherit board state or receive events.
3. Verify concurrent operations, duplicate IDs, changed-payload conflicts, and a
   dropped acknowledgment. Refresh and reconnect recover acknowledged state and
   settle pending operations without duplicate application effects.
4. Kill the owning replica, then separately the non-owning ingress replica, and
   restart each. Identify ownership immediately before each failure from runtime
   state; do not infer it from gateway selection. Record observed close codes and
   reconnect times, including lease/rebalance delay. Restart workerd and disconnect
   a browser too. Run a stated idle observation on the ordinary fleet, then a
   dedicated fleet with a small explicit CELLD_IDLE_EVICT_S: prove actual eviction
   before exercising attachment restoration and applying the next operation once.
   Record whether a room move closes the socket. No claim of sockets surviving
   process loss, or of unbounded idle behavior from a finite observation.
5. Approve compatible v2 with clients connected. One already-open v1 browser must
   send an operation handled by v2, identified in the reply. v2 accepts v1 pending
   messages and attachments; v1 clients ignore unknown server fields/types. Storage
   and receipt schemas stay compatible. Established sockets can mutate while HTTP
   routing is paused; this fixture uses no D1 migration. Test new-connection route
   gating separately. Contrast SSE: a running stream can be cancelled after celld's
   configured deployment maximum age, so test reconnection there as well.
6. Exercise `void/live` SSE separately through workerd, using the same room's
   `onRequest` GET as the authoritative snapshot source. Publish only revision hints
   after the durable acknowledgment, best effort; failed or stalled publication must
   not block it. On subscribe/resubscribe, fetch a snapshot after subscription
   registration succeeds, closing the snapshot-before-subscribe race. Events trigger
   refresh, with revision filtering against out-of-order snapshot responses. Test a
   missed event and publication failure. Pruning alarms may run while routes pause;
   they only clean subscriptions and do not qualify arbitrary scheduled effects.
   Record cancellation/idle behavior. Keep this item open if a separate fix is needed.
7. Stop clients, take a stopped snapshot and restore fresh storage; reconnect and
   verify board and receipt preservation. Check the explicit lower-revision error
   behavior separately. Existing offline retirement contracts remain unchanged;
   changing a route alone is not a revocation mechanism for established streams.
8. Run ordinary offline Void and fogd builds for the same source, plus browser and
   focused failure tests. Document the protocol, observed boundaries, and reproduction.

Do not add a general event broker, CRDT, arbitrary event log, platform websocket
replay, or a new distributed-state service. Keep transport and durable application
state separate. M11 scheduled/workflow/alarm activation remains its own later slice.


## Initial transport evidence

The [minimal native-room probe](evidence/m11b-native-websocket.json) passes ordinary
scoped upload, exact approval, HTTP access and a Chromium WebSocket exchange through
workerd. It uses `defineRoom` and inferred `ChecklistWs` resources without a shim.
This proves basic transport only, not durable acknowledgments, reconnection, or SSE.

To reproduce on a fresh disposable fixture (after installing workspace dependencies):

```sh
FOGD_PROBE_HTTP_PORT=8903 FOGD_PROBE_ADMIN_PORT=8904 \
  node scripts/queue-probe/setup.mjs .fogd/live-fixture fogd-m11-live
FOGD_ENV_FILE="$PWD/.fogd/live-fixture/probe.env" \
  node scripts/live-native.mjs .fogd/live-transport
```

Use unused ports, project names and output directories. The setup's queue opt-in is
irrelevant to this nonqueue room; it reuses the existing disposable two-fleet builder.
If Docker's address pools are exhausted, stop/remove only completed disposable
projects' containers and networks, retaining their volumes and evidence.
