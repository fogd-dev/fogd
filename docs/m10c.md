# M10c: measured Docker capacity and fleet expansion

Original proposal retained for the review record. Current qualification and limits:
[expansion guide](expansion.md) and [report](report.md#m10c-three-fleet-expansion).

Status at proposal time: proposed. Capacity measurement precedes expansion; three concurrent apps
are not yet qualified. M10a admission accounting and M10b retirement remain the
current supported contracts.

## Outcome

An operator can budget a small installation and run three approved applications
at once, while retaining stopped backup, restore, and retirement. The first
qualification target is Docker on one host. Kubernetes remains on its separately
qualified two-fleet topology.

## Measurement contract

Capture an explicit Compose project's running containers by label, without
recording credentials or full container inspection output. Record Docker engine
CPU/memory capacity, unrelated running-container count, image identities,
configured memory/CPU ceilings, restart counts, and timestamped Docker statistics.
Group gateway/controller/bucket as shared overhead and each two-replica fleet
separately. Report observed memory ranges and sampled CPU percentages; ceilings
are not reservations, observed memory is not a maximum safe capacity, and a short
sample is not a production sizing recommendation.

Reject missing required services, unexpected services, duplicate replicas,
container replacement, or restarts during a capture. An observation interval must
contain at least three samples. A delayed interval is visible in timestamps;
measurements taken across host sleep cannot qualify latency or availability.
Validation: capture the existing two-app installation without modifying it;
exercise malformed/missing statistics and service inventory with unit tests.

Before expansion, record both an idle window and a bounded, successful HTTP load
window with request counts, errors, latency percentiles, concurrency, duration,
and explicit request target. Load must use certificate verification. It must not
create unbounded records or artifacts. Validation: a reproducible read-only app
endpoint workload and an archived summary linked from the capacity guide.

## Proposed expansion boundary

Generate a complete Compose installation for an explicitly selected fleet count,
initially bounded to two or three. Each fleet retains two replicas, a private
network, two durable volumes, distinct node identities, and a distinct bucket
prefix. The controller, gateway, and bucket join each fleet network. Keep existing
resource ceilings; total configured ceilings must be shown to the operator.

Derive recovery inventory from a validated topology instead of extending fixed
lists piecemeal. Validate slot IDs, node services, volumes, network membership,
bucket-prefix uniqueness, and required shared services. Backup must cover every
writer and replica. Restore must reproduce the entire selected topology.
Retirement must clear only its selected fleet and preserve every other fleet.
Existing two-fleet bundles remain readable. Kubernetes must reject unsupported
fleet counts rather than accept an unqualified configuration.

Validation: deploy three differently named apps through scoped credentials and
approval; verify all routes and isolated durable data; restart the gateway and a
replica; stop and restore the complete installation onto fresh resources; retire
one app through a fresh restore and verify both surviving apps plus a replacement.
Capture capacity measurements at two and three fleets under the same workload.

## Alternatives and costs

Keeping two fleets avoids new topology and recovery code but requires retirement
before another app can be added. Sharing a celld fleet among apps might reduce
memory costs, but changes app/resource isolation and deployment ownership; it
requires its own design and qualification. An elastic scheduler adds placement
and lifecycle obligations before this small-host capacity is understood.

The proposed fixed three-fleet extension preserves current isolation at the cost
of two more celld processes and volumes per app. The operator bears memory, disk,
backup downtime, and retained-snapshot costs. If measurements make this unsuitable
for a modest host, reconsider density before adopting the extension. No monthly
price, production app count, or availability guarantee follows from laptop data.
