## Product outcome

An app periodically refreshes stored information while nobody has its page open.
Its users can see the last successful refresh and whether work failed. The operator
can approve a new release, stop new scheduled work, and recover the installation
without accidentally releasing restored or unapproved work.

The fixture uses native Void cron discovery, a stored result and an occurrence
ledger keyed by job, cron expression and scheduled time. Two jobs share one
expression, with a controlled failure in one: Void retries can rerun its successful
sibling, so expression-level deduplication is insufficient. A local source supplies deterministic test data; the example needs no
external account. The ledger demonstrates application idempotency, not an
exactly once guarantee for arbitrary external effects. Native scheduled handlers
and ordinary Void builds remain the preferred programming contract.

## Required behavior and evidence

1. A scoped CLI upload is inert before exact approval. On first activation, D1
   schema and required secrets exist before any scheduled handler executes. Test a
   real minute boundary before approval and during a deliberately delayed migration.
   Repeat with controller termination at publication and activation boundaries.
2. Approval pins the release and secret revision before any runtime side effect.
   After an uncertain write or lost runtime response, the controller exposes the
   uncertainty and does not silently activate another artifact. Test retry of the
   original artifact and an explicitly corrected artifact where supported.
3. Define the dispatch authorization boundary independently of HTTP routing. A
   persisted operator pause prevents new scheduled callbacks after confirmed pause;
   document whether already-running callbacks and `waitUntil` work can finish.
   Test a held callback, an unreachable replica, controller restart and runtime
   restart. Do not label routing pause as timer pause or an observation as a fence.
4. Compatible replacement has an explicit old/new handler overlap contract. Prove
   which release handles a new occurrence and what happens to an in-flight old
   callback. Preserve the application occurrence key across retries. Test a result
   committed before a lost acknowledgment, and assert no duplicate business row.
5. Measure native successful execution, thrown failure, `noRetry`, retry followed
   by eviction or owner loss, and extended downtime. Record scheduled time versus
   attempt time, skipped or superseded occurrences, and terminal failure. A manual
   HTTP trigger alone does not satisfy this gate. Never imply all missed ticks are
   retained unless the implementation and evidence establish that contract.
6. Operator status separates desired dispatch state, observed runtime state,
   approval progress and application outcomes. Test that private secrets and
   credential values never enter artifacts, status or ordinary errors. The example
   displays its last successful refresh and a useful failed-work state.
7. A stopped full-installation snapshot restores onto fresh storage with dispatch
   held until explicit acknowledgment/resume. Test a due timer and pending retry,
   including an older snapshot. State the loss boundary and possible external-effect
   replay. Restore must not boot an active timer before recovery controls take hold.
8. Retirement prevents future dispatch and reuse cannot inherit the old schedule,
   ledger, secret authority or data. Test surviving apps and a replacement app.
   Expansion and unsupported topology recovery reject scheduled history until each
   has equivalent evidence; such refusals are gaps, not qualification of those paths.
9. Build the same fixture through ordinary Void and fogd with networking disabled.
   Record generated declarations and every adapter or runtime patch. Native Docker
   qualification uses two nodes and workerd ingress; it includes replica failure
   and independently checked runtime state. Hosted Cloudflare execution is excluded.

## Selected architecture

The [review response](reviews/m11c-design-response.md) selects a migration-safe
bootstrap and a native durable dispatch-control primitive. It rejects whole-app
stop policy and a second fogd scheduler as the product control mechanism. A source-only or runtime-only experiment can inform the choice,
but does not complete this milestone. The selected design must explain how it
satisfies each gate or record a specific unresolved requirement before admission.

Independent scheduler semantics, timer pause and retry retention are different
contracts. A paused callback that throws is not automatically retained: the pinned
celld scheduler can discard retry identity on eviction or when the next occurrence
wins. Preventing dispatch must not masquerade as durable queuing of every tick.

## Following slices

Workflows need step execution, replay, external-effect idempotency and recovery
qualification. General Durable Object alarm governance must account for already
admitted classes and existing timers. Neither is completed by this cron slice or
by SSE subscription cleanup. Remote infrastructure and broader portability remain
on the [roadmap](roadmap.md).
