# M8b2: native TLS and an explicit shared profile

Qualify encrypted app/admin ingress and the controlled shared profile on local Docker.
Keep native Void secure-session behavior and carry transport state through the M8a
recovery path. This does not qualify a hostile-tenant PaaS or a two-host network.

## Proposed architecture

Terminate app TLS in workerd's native HTTPS socket and admin/deploy TLS in Node's
HTTPS server. Use operator-supplied PEM certificates and private keys. Avoid adding
a reverse proxy solely for TLS. The workerd schema already exposes HTTPS sockets
and TlsOptions.keypair; Node has the required server support.

Add a dedicated managed `tls` volume, mounted read-only by controller and workerd.
An operator CLI imports a matching certificate/key through stdin to a fixed-path
helper while the project is stopped. Validate key match and certificate validity
without printing private material. A local test certificate is generated only inside
the repo, with no system trust-store changes. ACME/certificate renewal is external.
The recovery topology must support the original six volumes and the optional TLS
volume, preserving its private state and exact image identities.

Separate the controller's private routing listener from public admin/deploy ingress.
The internal HTTP listener exposes only gateway-authenticated routing; the public
listener does not expose `/internal/route`. Docker publishes only the public ingress.
Update workerd's configured controller address to the internal listener. Runtime
and bucket ports stay on private Compose networks.

celld does not terminate TLS and defaults request URLs to http. Its pinned source
supports `--trust-forwarded-headers`. Enable it only behind fogd's gateway, which
must strip client forwarding headers and replace both X-Forwarded-Proto and
X-Forwarded-Host from the request URL it actually received. Native workerd TLS then
preserves the application's HTTPS origin without trusting a client's spoofed scheme.
Test this with Void secure session cookies, not only a health response.

## Profiles and operator workflow

Local mode keeps the existing loopback HTTP workflow. Shared mode requires TLS and
scoped deployment credentials; it refuses the legacy installation-wide deploy token.
A non-loopback published address requires the shared profile. Pass the declared host
binding into the platform services so startup can validate this policy. Invalid
profile/TLS settings fail closed.

The CLI must not silently regenerate a legacy token in shared mode. Provide an
explicit shared startup path and document how an administrator imports certificates,
sets the app domain/admin endpoint, issues scoped tokens, and starts the stack.
The default local operator continues to use the current quickstart.

The teammate CLI uses explicit `FOGD_SERVER` and `NODE_EXTRA_CA_CERTS` for a private
CA. No global TLS verification bypass. Test certificate rejection without trust and
successful deploy/status with trust. Browser test trust must be confined to the
test browser; preserve normal TLS verification for actual clients.

## Acceptance

Deploy the accounts fixture through HTTPS with a scoped credential and separate
admin approval. Browser signup/login uses Secure cookies and maintains the correct
HTTPS origin. Client-supplied forwarded headers cannot downgrade the origin or change
app routing. Public internal-route access is refused, while private gateway routing
works. Plaintext public binding, missing certificates, legacy shared credentials,
and wrong certificate trust fail explicitly.

Start from an M8a backup, upgrade the controller/gateway configuration deliberately,
and retain app data/approval evidence. Restore a TLS/scoped-credential installation
onto fresh volumes and verify login, credentials/revocation, quotas, and certificate
trust. Pin existing celld/workerd versions; this is a fogd control-plane upgrade,
not an upstream-runtime upgrade claim. Keep all real deployment evidence local and
record private-network, certificate-renewal, and single-admin limitations.
