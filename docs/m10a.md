# M10a: explain installation capacity before changing ownership

This slice gives operators an accurate view of admission capacity. It advances
operability without implying that an old app can already be deleted or its slot
reused. Retirement and generation-safe reuse remain M10b work.

## Operator scenario

An administrator has two apps and receives a request to host another. The admin
page and CLI should explain whether the limit is app slots, pending submissions,
or retained artifact bytes. A paused or quarantined app still owns capacity.
Pending proposals do not reserve slots; final admission occurs at approval.

## Contract and evidence

| Requirement | Validation |
| --- | --- |
| Admin API reports configured, occupied, and available slot counts, plus each slot's owning apps and route/quarantine state | Controller fixture covers empty, active, paused, quarantined, and bucket-owned orphan slots |
| Bucket ownership or controller assignment keeps a slot occupied | Simulate missing controller metadata and duplicate ownership; neither is reported available |
| Pending and failed requests count against admission limits, with global and per-credential counts | Compare report with submit refusal at each boundary; rejected/superseded requests do not count |
| Retained artifact bytes use existing admission accounting and explicitly exclude app data and filesystem allocation | Restart controller and compare report with files; no claim of free disk bytes |
| Admin CLI and page expose the same capacity snapshot | HTTP/CLI checks compare API data; page escapes app and slot labels |
| Report exposes no deploy-token hashes, secrets, bucket credentials, or internal replica addresses | Auth and response-field tests cover admin and deploy-only callers |
| Reporting is read-only and does not reserve, release, or delete anything | Compare ownership and deployment state before/after repeated requests |

Use the existing admin endpoint and authentication. The CLI command is
`fogd admin capacity`. Counts are observations, not reservations or promises that a
subsequent approval will succeed. Existing approval rechecks remain authoritative.
A report is not a measurement of CPU, memory, bucket consumption, or cost.

## Remaining M10 slices

M10b must define app retirement, retained export/backup ownership, stopped writers,
credential revocation, historical artifact retention, and fresh namespace/disk
identities before reuse. Pausing routing alone cannot stop alarms or existing work.
No deletion or ownership release belongs in M10a.

M10c must measure per-app runtime resources and shared overhead under a documented
workload before changing slot count or promising density. Current topology has two
fixed replica fleets; more slots require matching runtime/network/storage config,
not merely a larger controller array.
