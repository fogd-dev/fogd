# Codex architecture review

**Request changes before closing milestone 1.** The chosen topology is feasible, but the deployment and security boundaries need correction. I verified all three pinned revisions and inspected `.upstream` directly.

1. **[P1] “Only the deploy controller holds bucket credentials” cannot work.** Every celld replica accesses the bucket for ownership, deployment loading, persistence, and R2. Its R2 implementation explicitly uses the fleet’s credentials. Give replicas credentials scoped to their app’s bucket/prefix; reserve storage provisioning credentials for the controller. Keep credentials out of submitted bundles and build containers. [r2_ops.rs:3](../../.upstream/celld/crates/celld/js/r2_ops.rs:3)

2. **[P1] Bundle approval does not establish tenant isolation.** celld explicitly trusts application code. Its internal listener exposes unauthenticated operations, including shutdown and direct access to ordinary Durable Objects, while worker fetches can make network requests. Putting every app on one Compose network would expose these interfaces across apps. State that v0 runs trusted, approved code; isolate each fleet’s network, expose only the public listener to workerd, and publish no internal ports. Network separation still does not isolate an app from its own celld process’s operator interface. Hostile tenant isolation requires additional work. [security.md:7](../../.upstream/celld/docs/security.md:7), [main.rs:2870](../../.upstream/celld/crates/celld/main.rs:2870)

3. **[P1] Deployment publication, adoption, and migration readiness need separate gates.** `celld deploy` publishes queue attachments and then live deployment pointers. Nodes adopt independently; a failed adoption leaves the previous generation serving. Consequently, successful deployment plus HTTP health does not prove either replica serves the intended release. Withholding a hostname also does not prevent background execution. For existing databases, apply backward-compatible migrations before publication. Define a bootstrap sequence for new databases and background consumers. Verify the expected version on both replicas through `/reload` results or equivalent version reporting before declaring success. Do not imply atomic rollout or schema rollback. [deploy.rs:924](../../.upstream/celld/crates/celld/deploy.rs:924), [main.rs:886](../../.upstream/celld/crates/celld/main.rs:886)

4. **[P1] R2 multipart is not portable across the proposed replicas.** Upload handles live in a process-local map. `resumeMultipartUpload()` explicitly cannot resume across nodes or restarts. A multipart API spanning several HTTP requests can therefore fail under ordinary load balancing, without any outage. Change this matrix entry to **Partial**, or split ordinary object operations from multipart. The smallest v0 adjustment is to exclude resumable multipart and use single-request streamed uploads. Affinity can support multipart during normal operation but cannot provide restart recovery. [r2_ops.rs:366](../../.upstream/celld/crates/celld/js/r2_ops.rs:366), [r2_ops.rs:447](../../.upstream/celld/crates/celld/js/r2_ops.rs:447)

5. **[P2] SQL packaging needs an explicit translation contract.** Void excludes `seed.sql`, sorts migrations lexicographically, and tracks `_void_migrations`. celld reads SQL files using numeric-prefix order and defaults to `d1_migrations`; copying a directory containing `seed.sql` causes rejection. Switching runners can also reapply migrations because their ledgers differ. Package exactly Void’s migration list, validate compatible ordering, and choose one authoritative runner/ledger. Explicitly handle or exclude generated auth migrations, which Void runs separately from application SQL. [collect.ts:7](../../.upstream/void/packages/void/src/migrations/collect.ts:7), [migration-handler.ts:108](../../.upstream/void/packages/void/src/runtime/migration-handler.ts:108), [d1_cli.rs:267](../../.upstream/celld/crates/celld/d1_cli.rs:267)

6. **[P2] A stable prefix alone does not preserve resource identity.** Durable Object namespaces include the script and class names. D1 identity uses `database_id`, falling back to `database_name`. Renaming these can silently select empty state inside the same prefix. Persist the app’s resource identity mapping and reject accidental changes during redeployment; keep release IDs out of resource names too. [engine_api.rs:545](../../.upstream/celld/crates/celld/engine_api.rs:545), [deploy.rs:1201](../../.upstream/celld/crates/celld/deploy.rs:1201)

7. **[P2] Pin and qualify MinIO before relying on persistence tests.** Upstream documents that `RELEASE.2025-09-06T17-38-46Z` breaks conditional creation and first deployment; it requires `RELEASE.2025-09-07T16-13-09Z` or later. Pin a tested image digest and run the conditional-write/range-read checks. Also preserve replica log volumes and implement restart supervision with the documented lease-aware delay. [guarantees.md:37](../../.upstream/celld/docs/guarantees.md:37), [guarantees.md:73](../../.upstream/celld/docs/guarantees.md:73)

Additional audit adjustments:

- Qualify D1 sessions as **primary-only**, with the fixed `celld:primary` bookmark. [harness.js:7823](../../.upstream/celld/crates/celld/js/harness.js:7823)
- The adapter must validate compatibility flags as well as binding names: celld accepts unsupported flags without effect. [cloudflare-compat.md:204](../../.upstream/celld/docs/cloudflare-compat.md:204)
- Separate managed TLS provisioning from TLS termination: workerd supports HTTPS listeners with supplied certificates. [workerd.capnp:144](../../.upstream/workerd/src/workerd/server/workerd.capnp:144)
- Idempotency keys require durable server-side deduplication tied to the mutation; merely forwarding a client header is insufficient.

Keep one fleet per app and workerd ingress. For two-machine portability, parameterize bucket endpoints and peer advertised addresses now; Compose service names alone will not span hosts. The proposed corrections require neither Cloudflare APIs/credentials nor npm publishing.

This was a source review only. I made no edits and ran no deployment or failure tests.
