### Priority 1 (High) — Resource Reservation & Failure Semantics

1. **`controller.mutate()` clobbers `request.resourceChanges` on initial approval, retry approval, and post-failure recovery submissions ([controller.mjs](file:///Users/sgtpooki/code/sgtpooki/fogd/packages/platform/src/controller.mjs#L113-L130))**
   - **Initial deploy approval:** At [controller.mjs:113-118](file:///Users/sgtpooki/code/sgtpooki/fogd/packages/platform/src/controller.mjs#L113-L118), when `!app`, `app` is initialized with `resources: request.resources` (by reference, not cloned) and saved *before* line 118 runs `request.resourceChanges = this.compatible(request, app)`. Because `app.resources` now equals `request.resources`, `resourceChanges(app.resources, request.resources)` immediately overwrites `request.resourceChanges.r2Added` with `[]`.
   - **Retry after failed activation:** At [controller.mjs:129-130](file:///Users/sgtpooki/code/sgtpooki/fogd/packages/platform/src/controller.mjs#L129-L130), `app.resources = structuredClone(request.resources)` persists the new floor before `publish()` / `migrate()`. When activation fails and the administrator retries that deployment (`mutate(id, digest, 'approve')`), line 118 recomputes `this.compatible(request, app)` against the already-advanced `app.resources`, overwriting `request.resourceChanges` with `{ r2Added: [] }` and erasing the derived R2 additions from `/v1/admin` and the approval UI ([http.mjs:68](file:///Users/sgtpooki/code/sgtpooki/fogd/packages/platform/src/http.mjs#L68)).
   - **Replacement release after rejecting a failed activation:** When a release that added an R2 binding fails activation and is rejected, `app.resources` retains the reservation floor. A subsequent corrected submission has its `resourceChanges` diffed against `app.resources` rather than the active release (`this.state.deployments[app.active]?.resources`), so `r2Added` is `[]` even though the new R2 binding has never been activated.
   - **Side effects before approval validation completes:** In [controller.mjs:111-119](file:///Users/sgtpooki/code/sgtpooki/fogd/packages/platform/src/controller.mjs#L111-L119), `backend.claim(slot, request.app)`, `this.state.apps[request.app] = app; await this.save()`, and `this.reconcile(app, slot)` execute *before* `this.compatible(request, app)` (line 118) and the second `artifactDigest` check (line 119). Compatibility and digest checks should gate `claim()` and state creation.

2. **Derived R2 `bucket_name` length (`> 64` chars) and unsupported R2 config keys are accepted at submission/reservation time but rejected by `celld deploy`, permanently bricking the app's monotonic resource floor ([artifact.mjs](file:///Users/sgtpooki/code/sgtpooki/fogd/packages/runtime/src/artifact.mjs#L12-L76), [deploy.rs](file:///Users/sgtpooki/code/sgtpooki/fogd/.upstream/celld/crates/celld/deploy.rs#L1815-L1829))**
   - [artifact.mjs:12](file:///Users/sgtpooki/code/sgtpooki/fogd/packages/runtime/src/artifact.mjs#L12) allows `app` names up to 63 chars and [artifact.mjs:22](file:///Users/sgtpooki/code/sgtpooki/fogd/packages/runtime/src/artifact.mjs#L22) allows arbitrary-length `binding` identifiers, deriving `bucket_name: `${app}-${binding.binding.toLowerCase()}`` ([artifact.mjs:75](file:///Users/sgtpooki/code/sgtpooki/fogd/packages/runtime/src/artifact.mjs#L75)).
   - However, `celld deploy` enforces `valid_resource_name(bucket_name)` with a hard 64-character maximum ([deploy.rs:1815-1819](file:///Users/sgtpooki/code/sgtpooki/fogd/.upstream/celld/crates/celld/deploy.rs#L1815-L1819), [deploy.rs:2299-2309](file:///Users/sgtpooki/code/sgtpooki/fogd/.upstream/celld/crates/celld/deploy.rs#L2299-L2309)). If `${app}-${binding.toLowerCase()}` exceeds 64 chars, `submit()` and approval validation succeed, `controller.mjs:129` permanently persists the R2 binding into `app.resources`, and `celld deploy` then fails in `publish()`. Because the spec forbids removing or renaming reserved R2 bindings even after failed activation, the app becomes permanently unrecoverable.
   - Similarly, unlike `durable_objects`, `migrations`, and `assets` ([artifact.mjs:49-59](file:///Users/sgtpooki/code/sgtpooki/fogd/packages/runtime/src/artifact.mjs#L49-L59)), `translateConfig` does not call `keys(...)` on `input.r2_buckets` or `input.d1_databases` entries, silently dropping unsupported fields like `jurisdiction` (which [deploy.rs:1827-1829](file:///Users/sgtpooki/code/sgtpooki/fogd/.upstream/celld/crates/celld/deploy.rs#L1827-L1829) explicitly refuses).

3. **`resourceChanges()` does not enforce append-only ordering on `r2_buckets` and test coverage omits rejecting a failed release ([resources.mjs](file:///Users/sgtpooki/code/sgtpooki/fogd/packages/platform/src/resources.mjs#L4-L15), [platform.test.mjs](file:///Users/sgtpooki/code/sgtpooki/fogd/packages/platform/test/platform.test.mjs#L208-L239))**

   - The spec states: *"It becomes the minimum declaration for future submissions, even if activation fails or the failed release is rejected. Recovery requires a corrected release retaining those declarations."* [platform.test.mjs:208-239](file:///Users/sgtpooki/code/sgtpooki/fogd/packages/platform/test/platform.test.mjs#L208-L239) tests rejecting a *pending* release and retrying a *failed* release, but never tests rejecting a *failed* activation (`mutate(failed.id, failed.digest, 'reject')`) and recovering via a new corrected submission.
   - Note also the interaction with [controller.mjs:103](file:///Users/sgtpooki/code/sgtpooki/fogd/packages/platform/src/controller.mjs#L103): for an already-active app (`app.active !== null`), `migrate()` runs *before* `publish()` ([controller.mjs:131-137](file:///Users/sgtpooki/code/sgtpooki/fogd/packages/platform/src/controller.mjs#L131-L137)). If activation fails or is interrupted during `checking-migration-ledger` or `migrating` while the replica is unreachable (so `catch`'s `reconcile()` at line 145 also fails), `app.uncertain` remains set to `id`, which blocks `mutate(id, digest, 'reject')` until a subsequent approval reconciles the ledger.

### Priority 2 (High) — Bounded Logical Transfer & Quiescence Semantics

4. **Void's route scanner ignores `_`-prefixed path segments, so `/__fogd/*` handlers cannot be placed in `routes/__fogd/` ([plugin-inference-Bekzjuqw.mjs](file:///Users/sgtpooki/code/sgtpooki/fogd/node_modules/.pnpm/void@1.1.11_@types+node@26.6.5_arktype@2.2.8_kysely@0.29.6_react-dom@19.3.1_react@19.3._d3d8cd224693688cc99289ea25e62dc9/node_modules/void/dist/plugin-inference-Bekzjuqw.mjs#L33-L35), [gateway.js](file:///Users/sgtpooki/code/sgtpooki/fogd/packages/runtime/src/gateway.js#L20-L22))**
   - The spec requires *"app-specific handlers under `/__fogd/`, blocked at the public gateway."* While [gateway.js:20](file:///Users/sgtpooki/code/sgtpooki/fogd/packages/runtime/src/gateway.js#L20) blocks `/^\/__(?:void|fogd)(?:\/|$)/`, Void's `listConventionFiles(paths.routesDir)` filters out any route file with a `_`-prefixed path segment (`!filePath.split("/").some(segment => segment.startsWith("_"))`).
   - Consequently, files under `routes/__fogd/...` are silently ignored by the Void build. In a native Void app, `/__fogd/*` must be served via a non-underscore file in `middleware/` (e.g., `middleware/fogd-transfer.ts`, since `parseMiddlewareDefinitions` in [application-analysis-D7nNmNJb.mjs:180-181](file:///Users/sgtpooki/code/sgtpooki/fogd/node_modules/.pnpm/void@1.1.11_@types+node@26.6.5_arktype@2.2.8_kysely@0.29.6_react-dom@19.3.1_react@19.3._d3d8cd224693688cc99289ea25e62dc9/node_modules/void/dist/application-analysis-D7nNmNJb.mjs#L180-L181) also skips `_`-prefixed filenames). User middleware runs inside `withRuntimeEnv` and `requestMiddleware` ([index.mjs:2202-2215](file:///Users/sgtpooki/code/sgtpooki/fogd/node_modules/.pnpm/void@1.1.11_@types+node@26.6.5_arktype@2.2.8_kysely@0.29.6_react-dom@19.3.1_react@19.3._d3d8cd224693688cc99289ea25e62dc9/node_modules/void/dist/index.mjs#L2202-L2215)) and is scanned by `inferProjectBindings` ([plugin-inference-Bekzjuqw.mjs:573-582](file:///Users/sgtpooki/code/sgtpooki/fogd/node_modules/.pnpm/void@1.1.11_@types+node@26.6.5_arktype@2.2.8_kysely@0.29.6_react-dom@19.3.1_react@19.3._d3d8cd224693688cc99289ea25e62dc9/node_modules/void/dist/plugin-inference-Bekzjuqw.mjs#L573-L582)), so `void/db` and `void/storage` work natively there.

5. **Partial-restore visibility and retryability across non-transactional R2 + D1 writes ([storage.rs](file:///Users/sgtpooki/code/sgtpooki/fogd/.upstream/celld/crates/celld/storage.rs#L3001-L3049), [r2_store.rs](file:///Users/sgtpooki/code/sgtpooki/fogd/.upstream/celld/crates/celld/r2_store.rs#L531-L566))**
   - The spec requires: *"Validate an entire import before writes. Restore only into an empty destination; use a completion record or idempotent state checks so an interrupted restore cannot silently produce duplicates or make a partial dataset look complete."*
   - If the restore handler executes multiple sequential D1 `INSERT` calls (`await db.insert(...)`), an interruption mid-import leaves a partial subset of `messages`/`attachments` committed in D1. Unless the public routes (`GET /`, `GET /api/messages`) also query a completion table on every request, those routes will immediately serve the partial dataset as if it were complete.
   - Conversely, if the restore handler writes an "in-progress" row to D1 (or checks `storage.list()` for emptiness) *before* writing R2 objects and fails mid-R2-upload, a non-idempotent emptiness check will permanently reject retries on that destination slot.
   - **Concrete design requirement:** After full up-front validation of the import payload in memory and verifying that D1 is empty (and no completed restore marker exists), the restore handler should:
     1. Write all R2 objects first by deterministic key (overwriting any orphan R2 objects from a prior interrupted attempt, passing `{ sha256 }` to `storage.put` so [r2_store.rs:537-540](file:///Users/sgtpooki/code/sgtpooki/fogd/.upstream/celld/crates/celld/r2_store.rs#L537-L540) verifies the digest at the storage layer).
     2. Commit all D1 `messages`, `attachments`, and completion state in a **single `D1Database.batch(...)` call**, which `celld` executes inside a single SQLite transaction (`D1Request::Batch` in [storage.rs:3001-3049](file:///Users/sgtpooki/code/sgtpooki/fogd/.upstream/celld/crates/celld/storage.rs#L3001-L3049)). That way, D1 transitions atomically from empty to complete after all R2 objects are durable.

6. **Quiescence via replica stop/restart requires graceful `SIGTERM` (never `-t 0` across both replicas) and post-restart readiness polling ([main.rs](file:///Users/sgtpooki/code/sgtpooki/fogd/.upstream/celld/crates/celld/main.rs#L4982-L5496), [celld-supervisor.sh](file:///Users/sgtpooki/code/sgtpooki/fogd/docker/celld-supervisor.sh#L9-L13), [compose.yaml](file:///Users/sgtpooki/code/sgtpooki/fogd/compose.yaml#L19-L31))**
   - Unlike [recovery.mjs:51](file:///Users/sgtpooki/code/sgtpooki/fogd/scripts/recovery.mjs#L51) (which uses `docker compose stop -t 0` on one replica at a time while its peer remains alive), stopping **both** replicas of a slot with `-t 0` (`SIGKILL`) skips `durability_owner.quiesce_and_seal_within` ([main.rs:5482-5496](file:///Users/sgtpooki/code/sgtpooki/fogd/.upstream/celld/crates/celld/main.rs#L5482-L5496)) and can drop unshipped D1 LTX frames if called immediately after a write. Stopping/restarting replicas for transfer quiescence must use graceful `SIGTERM` (`docker compose stop` / `restart` without `-t 0`).
   - When both replicas of a slot receive `SIGTERM` simultaneously, both set `app.draining = true` ([main.rs:4935](file:///Users/sgtpooki/code/sgtpooki/fogd/.upstream/celld/crates/celld/main.rs#L4935)) and serialize on the bucket drain token ([main.rs:4982-5043](file:///Users/sgtpooki/code/sgtpooki/fogd/.upstream/celld/crates/celld/main.rs#L4982-L5043)) before sealing their node logs; upon restart, [celld-supervisor.sh:9-12](file:///Users/sgtpooki/code/sgtpooki/fogd/docker/celld-supervisor.sh#L9-L12) sleeps `FOGD_RESTART_DELAY_SECONDS` (15s) before starting `celld`. The transfer operator must wait for replica readiness (`:8081/reload` for the active version + `:8080/.well-known/celld/health`, matching [backend.mjs:43-58](file:///Users/sgtpooki/code/sgtpooki/fogd/packages/platform/src/backend.mjs#L43-L58)) after restarting replicas before invoking `/__fogd/export` or `/__fogd/import`.

### Priority 3 (Medium) — Transfer Validation, Checksums & Limits

7. **`celld` R2 does not compute or store `sha256` on `R2Object.checksums` unless asserted at `put` time, and export must verify live R2 bytes against SQL metadata ([r2_store.rs](file:///Users/sgtpooki/code/sgtpooki/fogd/.upstream/celld/crates/celld/r2_store.rs#L285-L310))**
   - In [r2_store.rs:285-310](file:///Users/sgtpooki/code/sgtpooki/fogd/.upstream/celld/crates/celld/r2_store.rs#L285-L310), `Digests::wanted` only computes `md5` by default; `sha256` is only computed and stored in the R2 envelope if the caller passed a `sha256` digest in `R2PutOptions`.
   - Furthermore, relying on stored metadata alone during `/__fogd/export` would miss a missing or corrupted R2 object. `/__fogd/export` should stream/read the bytes of each SQL-referenced attachment via `storage.get(key)`, fail if any referenced object is missing in R2 or exceeds the export byte budget, and compute/verify the SHA-256 and byte length over the actual exported bytes.

8. **Explicit transfer limits must account for `celld` request-body and V8 heap bounds, and validate `AUTOINCREMENT` ID bounds ([compose.yaml](file:///Users/sgtpooki/code/sgtpooki/fogd/compose.yaml#L28-L31), [20261016160656_complete_ser_duncan.sql](file:///Users/sgtpooki/code/sgtpooki/fogd/examples/guestbook/db/migrations/20261016160656_complete_ser_duncan.sql#L1-L5))**
   - Each replica runs with `CELLD_MAX_REQUEST_BODY_BYTES=16777216` (16 MiB) and `CELLD_V8_HEAP_LIMIT_MB=128` ([compose.yaml:28-30](file:///Users/sgtpooki/code/sgtpooki/fogd/compose.yaml#L28-L30)). Because `/__fogd/import` receives the full export JSON (with base64-encoded attachment bytes) in a single HTTP request and validates the entire import in memory before writes, the profile's explicit total-byte limit must be sized well below 16 MiB after base64/JSON overhead (e.g., $\le 4\text{--}8\text{ MiB}$ raw attachment bytes).
   - Because `messages.id` (and `attachments.id` if integer-keyed) uses `INTEGER PRIMARY KEY AUTOINCREMENT` ([20261016160656_complete_ser_duncan.sql:2](file:///Users/sgtpooki/code/sgtpooki/fogd/examples/guestbook/db/migrations/20261016160656_complete_ser_duncan.sql#L2)), import validation must enforce positive safe integer IDs (`1 <= id < Number.MAX_SAFE_INTEGER`) in addition to uniqueness and referential integrity (`attachment.messageId` in `messages`), ensuring `sqlite_sequence` advances properly and the post-restore write cannot fail with a primary-key collision or `SQLITE_FULL`.
   - Because the private `/__fogd/*` call from the `controller` container bypasses `workerd` and `controller.route()`, the transfer operator must verify in controller state (`state.json` / `/v1/admin`) that both source and destination apps have `route === 'active'`, `!quarantined`, and `!uncertain` before invoking `/__fogd/export` or `/__fogd/import`.
