I found no blocking correctness bug in this slice for the privately seeded path. One availability issue needs a decision before queue admission opens. All 120 tests in `packages/platform/test/*.test.mjs` pass. I traced every durable write and the backend effect after it myself rather than relying on the description.

## What I checked and found correct

- **Nonqueue activation is unchanged.** `activateRelease` does the same publish → migrate → publish → finish sequence as before. `prepareQueue` and `markQueueApplication` do nothing when there are no queues, and `failed()` only skips reconciliation when `app.delivery` exists. The `request.secretRevision`, `privateConfiguration` and `route` assignments that `activate` used to repeat already happen in `prepareActivation`. `resourceIdentity` never sets a `queues` key, so the new `queues` check in `resources.mjs:6` compares undefined with undefined for existing apps.
- **The bootstrap cannot be republished over consumer code.** The phase only moves forward (pending → ready → application). The only reset is `!app.delivery`, and nothing deletes `app.delivery` once a claim is resolved: `rejectUnclaimed` only removes the app record while `app.claim` is still set, which is before any delivery exists. `markQueueApplication` is saved before every consumer publish, including the first activation. If that save fails, the storage latch stops the publish.
- **Pause is confirmed before any ledger write.** `prepareActivation` skips its early `reconcile` for queue requests, so the `CREATE TABLE IF NOT EXISTS d1_migrations` in `applied()` only runs after `delivery.hold()` has saved a confirmed pause.
- **Interruption between delivery release and the active pointer is handled.** `interruptQueueActivation` sets the hold again with `operation: 'pause'`, and startup pauses again without ever resuming. A lost resume response leaves the hold in place, and the next retry pauses first. Running the approved, migrated consumer in that window is the documented overlap, not a bug.
- **An existing nonqueue app cannot gain a queue on update**, because `resourceChanges` rejects adding `queues`. So the bootstrap is only reachable on an app with no `app.active`.
- **Storage failures stop all effects.** `deliveryFor`'s persist checks the controller storage latch, and the catch in `activateRelease` rethrows before any further save.

## Must resolve before admission (not bugs in this checkpoint)

1. **One queue fleet can stop the whole controller from starting.** `recoverQueueHolds` runs inside `init()` before either listener starts (`main.mjs:16-20`). The 180s `ready()` or a pause failure on one held app throws, so `route()` stops answering for every app. That breaks the three-app isolation contract in m11a.md.
   - Every reachable "held and possibly running" state at startup is running an approved consumer: an uncertain resume (new release, already migrated and ready), an update interrupted before its pause (old release, no migration yet), or an uncertain pause (before migration). Each retry pauses again before touching the ledger.
   - So aborting startup buys no safety the retry path doesn't already give. Prefer marking that one app (route paused, retry required) and continuing startup.
   - At minimum, skip phase `ready` the way `pending` is skipped (`queue-activation.mjs:39,43`). There is no consumer in that phase, and the only extra effect is a check that can fail.
2. **The 503 bootstrap might never pass readiness.** `ready()` requires `/.well-known/celld/health` to succeed. If celld passes that path through to the worker, the bootstrap's 503 for every path fails `ready()` forever. The app then stays in phase `ready` and, combined with item 1, the controller restart-loops. Settle this in the Docker proof before admission.
3. **A permanent hold has no way out.** `assertQueueDecision` refuses approve and reject for every other request of a held app, including pending submissions that never ran. With a migration that always fails, the app is stuck, and its unrejectable pending submissions keep counting toward the global `maxPending` (20), which affects other apps' submissions. This is the known "repair transfer" gap; it gets worse once uploads open.
4. **The capability marker is written too late for a downgraded controller.** `queueCapability` is added in `prepareQueue`, but `step('approved')` has already saved `app.resources.queues` before that. An older controller can't see queues in `resourceChanges` and would approve and publish a queue artifact unpaused. Once admission opens, write the marker when a queue artifact is admitted.
5. **Retirement does not refuse queue apps.** `retirementApp` accepts a held queue app when `uncertain` is null, and `recoverQueueHolds` skips retired apps. Retirement and isolation are listed as future work, but add a refusal for apps with `app.delivery` until that lands.
6. **The bootstrap copies artifact declarations as-is.** `resources.queues.producers` and `resources.d1` are passed through unvalidated, and `compatibility_date` isn't type-checked. Admission validation has to constrain these, along with stable per-app physical queue names, `dead_letter_queue`, and consumer options.

## Hardening I'd fold into this slice (small)

- **The bootstrap temp directory lands in the artifact store.** Without secrets, `execution` is `artifacts/<id>`, so `mkdtemp(join(dirname(artifact), …))` creates `artifacts/.queue-bootstrap-*` (`backend.mjs:64`). A SIGKILL during the up-to-180s publish leaves it behind. `quota.init` then counts its bytes and lists it as an unreferenced artifact ID in admin capacity. Use a controller-owned directory, such as the secrets `execution` root or a dedicated one.
- **A mismatched metadata restore can still republish the bootstrap.** If restored state is at step `approved` (queue resources saved, no `delivery`, claim already deleted) while the bucket holds a live consumer, ownership checks pass and the retry runs `!app.delivery` → publishes the bootstrap over the consumer. Guard the intent creation in `prepareQueue` with `app.active === null && !(await backend.hasDeployment(slot))`. It's one check and it closes this before backup/restore work begins.
- **`validateQueueState` doesn't check the hold owner.** A hold naming a missing deployment, or one from another app, makes the app permanently unapprovable with no diagnostic. Require that the hold is a deployment of the same app with status `failed` or `activating`.

## Test gaps

- An update interrupted at `preparing-activation` or `approved`: startup now pauses a queue that was running freely and binds the hold to a request that never did anything. This is intended but untested.
- Startup when phase is `ready` and `ready()` fails (the abort in item 1).
- Metadata boundaries not in the 18: `queue-bootstrap-intent`, `checking-migration-ledger`, the pause confirmation save, and the saves during `init` for the interruption and recovery. I traced each by hand and they recover correctly.
