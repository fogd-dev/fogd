**Verdict: ready to land as a test-only slice.** I found no correctness bugs that would make it pass or fail wrongly, and the private probe keeps its default behavior. A few claims are worded more strongly than the code proves, and one comment is wrong.

The evidence so far is consistent with a run in progress. `context.json` shows source project `fogd-m11a-public-1792438511400`, so the env was correctly pointed at the restored project that `queue-public.mjs` left behind. `pending.json` shows `backlogCount: 2`, `stored: 2`, `paused: true`, `status: accepted` and zero results. `snapshot/` and `restored/` exist. `recovery.json` hasn't been written yet, which is expected mid-run.

**What holds up**
- **Duplicate submissions are real.** `submit()` calls `queue.send` whenever the job isn't complete (`examples/imports/lib/jobs.mjs`). Two POSTs while paused really produce two queued messages. The backup observation and the restored queue are both checked for exactly 2.
- **"Drain both" is backed by evidence.** The new poll requires `[backlogCount, stored]` to reach `[0, 0]` after the job completes. Waiting for `stored` to hit 0 is the pattern the other queue probes already use (`queue-native.mjs`, `queue-recovery.mjs`).
- **The private default is unchanged.** The defaults `app='imports'`, `queueName='imports'`, `backlog=1` reproduce the old literals. The inspect URL now uses `probe.slot.nodes[0]`, which is `slot-1-a` for slot-1. The one real change is the extra `[0,0]` drain poll, which also runs for `queue-installation-recovery.mjs`. That makes the private probe stricter. It matches what `stored` does elsewhere, but call it out in the commit message rather than describing private behavior as untouched.
- **Destructive scope is limited to disposable projects.** The target must match `^fogd-m11…` and differ from the source. `restore` refuses an existing target (`requireFresh`). `down` is run without `-v`, so source volumes are kept.

**Findings**
1. **The "exactly two unique result rows" claim is vacuous as an idempotency proof** (`queue-public-recovery.mjs:37,39`). `import_results` has `PRIMARY KEY (job_id, position)` and the insert uses `ON CONFLICT DO NOTHING`. That means `results.length === 2` cannot fail even if the duplicate message ran the whole job a second time. The actual idempotency comes from the `status === 'complete'` early return in `processJob`, and nothing checks that. Fix: record `job.attempts` and assert it is 1 or 2 (2 if both replicas grab the messages at once). Or reword the PASS line to "the duplicate is absorbed; schema-bounded to two rows."
2. **`ordinaryCliArtifact: true` is hard-coded, not checked** (`:38`). The script never confirms the active deployment came from the scoped CLI upload rather than an adopted or staged artifact. Fix: read `/v1/admin` before the backup and assert the active deployment's submitter credential is scoped to `['imports-public']`, as `queue-public.mjs:42-43` does. Or match the deployment id and digest against the prior `public.json`, then save that id.
3. **The comment at `:34` is wrong, and the `down` may not be needed.** `compose down` removes the source project's containers as well as its network. `backup()` already leaves the source stopped, and the private sibling never runs `down`. Stopped containers don't hold host ports, so the restored target can still bind them. Either drop the `down` to keep the stopped source for forensics, as restore's own warning suggests, or keep it and fix the comment to "remove this stopped disposable project's containers and network; retain every volume."
4. **Hidden precondition.** The script only works when `FOGD_COMPOSE_FILE` points at the restored project left by `queue-public.mjs`, with that app's delivery paused and an empty backlog. The `initial` asserts catch a wrong setup, but a one-line header comment or a README run step would save the next operator a failed run.
5. **Nit: the job-inspection branch is now dead code.** Both callers pass `jobId`, so the parameterized `inspect` block in `installation-recovery.mjs` never runs. Delete it, or leave it if a caller without `jobId` is planned.

**Not issues:** setting `Content-Type` on GETs is harmless. The unencoded `jobId` at `:28` is UUID-safe. `--accept-possible-loss` in a no-loss scenario matches the existing helper.
