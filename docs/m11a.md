# M11a: queued work with an explicit deployment lifecycle

Status: the [bounded Docker queue slice is locally qualified](m11a-acceptance.md).
Admission remains supported opt-in by policy. This is the first slice of M11;
cron, Workflows, and live collaboration retain separate lifecycle contracts.

## Product outcome

A user submits a bounded import, leaves the page, and returns to either completed
results or a useful failure state. The app developer uses Void's typed queue API,
R2 for the input, and D1 for status/results. The operator can approve an update and
recover pending work without silently executing an unapproved consumer or applying
a new consumer against an unfinished schema.

This implements [scenario U7](product.md#u7-a-user-uploads-something-that-takes-time-to-process).
It is not a general job scheduler or a promise of exactly-once external effects.

## Source findings

At the pinned revisions in [compatibility](compat.md), Void's
`packages/void/src/runtime/queues.ts` supplies typed producers and
`plugin-worker-bindings.ts` emits producer/consumer configuration. Its
`queues/dispatch.ts` resolves logical names and unambiguous physical-name suffixes.
Preserve those semantics rather than introducing a fogd-only app queue API.

celld's `crates/celld/deploy.rs` publishes queue attachments naming an immutable
release before updating the fleet entrypoint. Its `queue_cli.rs` exposes
`info`, `pause`, `resume`, and `redrive`; these verbs also appear in the pinned
runtime binary's help output. In `js/harness.js`, `_setPaused` persists delivery
pause, and `_rearm` excludes new delivery while paused. This does not establish
that an already running consumer has finished. The `info` response provides
backlog, stored-row, and pause information, not a proven handler-drained receipt.

fogd's [activation code](../packages/platform/src/controller.mjs) publishes a first
release before D1 migrations so the backend is available. Updates migrate before
publishing the replacement. Today HTTP routing pauses during this sequence, but
that cannot gate background dispatch. Simply accepting `queues` is insufficient.

## Proposed bounded contract

Start with same-app queues and fixed, validated producer/consumer declarations.
Derive stable per-app physical names; include them in artifact validation, resource
history, approval display, and recovery. Reject cross-app consumers and unsupported
options explicitly. Removing or renaming a queue with retained work is outside this
slice. Existing manifests and nonqueue app deployment must keep working.

Before any first consumer publication, persist an operator delivery pause for every
queue that release can consume. Prove that this can happen on an otherwise empty
fleet. Keep delivery paused until migrations, publication, and replica readiness
complete. If upstream cannot enforce this order, do not implement a timing-based
workaround: record the gap and review a small upstream capability patch or a
narrower supported contract.

For updates, pause new deliveries before migrations. An already running handler may
finish under the previous approved release. Retain the existing additive schema
contract and require message/payload compatibility across the old and new release.
Do not call this a drain. Probe whether a stronger drain boundary is available;
otherwise document and test the overlap explicitly. No destructive migration,
exactly-once side effect, or instantaneous consumer replacement claim is allowed.

Persist activation progress before effects. Failure or controller restart must not
silently resume work before migration/publication checks. A timed-out resume can
have committed: represent that uncertainty, retry idempotently, and distinguish
HTTP route state from delivery state. Exact-artifact approval authorizes execution;
merely uploading an artifact must have no consumer effects.

Background pause is an operator control. App builders cannot alter it through fogd's
control plane. Initially prefer pause/status/resume with bounded diagnostics over
adding destructive purge or payload inspection. Any queue administration API needs
the same admin authentication and CSRF policy as deployment decisions.

## Probe before implementation

Use a disposable local two-replica fleet, with no production or current example
state. Pin the runtime image. Exercise upstream commands directly in that fixture;
do not loosen fogd's admission policy to make the probe work.

1. Pause a named queue before any app is deployed; publish a consumer, enqueue work,
   and prove no consumer effect until resume. Verify pause survives replica restart.
2. Hold a consumer in flight, pause delivery, and publish another approved version.
   Record which version completes each message and whether any handler runs before
   its migration gate. Inspect admission, timeout, settlement, and lease semantics.
3. Interrupt between pause, migration, publication, and resume. Determine what can
   be established after restart using supported runtime operations.
4. Snapshot a paused fleet with pending work, restore all logs/identities and bucket
   state, and verify work resumes only after the deliberate operator action.

Record the observations and obtain peer review before locking the lifecycle design.
If safe initial pause or recovery cannot be demonstrated, keep queues unsupported
and preserve a focused upstream issue/patch note. Continue independent M11 work;
do not substitute a passing HTTP demo for the background contract.

## Application acceptance

Build an `examples/imports` Void app with a bounded input and deterministic results.
The acceptance harness must cover submission acknowledgement, page reload, successful
completion, duplicate delivery, a retryable failure, terminal failure, and explicit
retry without duplicate business records. Acknowledging an import and scheduling it
are separate durable effects: design the retry/outbox boundary explicitly rather
than assuming a D1 write and queue send form one transaction.

Before exposing the binding, qualify scoped submission and exact approval, preapproval
inactivity, first-deploy migrations, additive update with pending/in-flight work,
consumer failure/restart, controller failure at activation boundaries, and stopped
backup/restore with queued work. Preserve existing three-app isolation and retirement
contracts. Retirement must retain old queue state without allowing its activation in
a replacement fleet. Run the same source through ordinary offline Void builds;
no Cloudflare credentials, APIs, or hosted execution are involved.

## Options to review

- Use upstream persistent queue pause plus explicitly compatible old-handler overlap.
  This is the preferred starting point if the probe establishes the first-publish
  and recovery gates. It preserves upstream behavior without claiming a drain.
- Add a small, clearly labeled upstream draining/activation capability if a required
  boundary is missing. Review its persistence and failure semantics before adoption.
- Defer queue admission and proceed with a narrower independent M11 slice if neither
  option is defensible. Keep the product scenario and gap visible in the roadmap.

Automatic scaling, external queue brokers, arbitrary background execution, cron,
Workflows, and client WebSocket reconciliation are outside M11a.
